О документе

Документ описывает техническую логику АРМ — что происходит в системе при каждом действии пользователя. Операторские телефонные скрипты и человеческое общение вынесены за скобки. Документ охватывает роли Оператора, Логиста и Начальника КЦ.

Источники: регламент оператора (MVP), регламент логиста (MVP), регламент начальника КЦ, таблица угроз и превентивных мер (24 инцидента), спецификация дашборда оператора, логиста и начальника КЦ.

⚠️
Конфиденциально
Документ содержит операционные алгоритмы и бизнес-логику. Передача третьим лицам без письменного согласия SSI запрещена.
👥
Роли и права доступа (RBAC)
ℹ️
Принцип разграничения
Оператор видит только свои заказы. Логист и начальник КЦ видят все заказы. Финансовые операции (возврат, отмена с возвратом) — исключительно начальник КЦ.
👑
Начальник колл-центра (Supervisor)
Расширенная версия дашборда оператора/логиста. Видит все заказы всех операторов. Единственный, у кого активна кнопка возврата денег через Click API.

👤
Оператор
Видит только заказы, назначенные на его operator_id. Все финансовые решения эскалируются начальнику КЦ через «Запрос на отмену». Может давать примечания по чужим заказам (только если принял звонок), но не изменять статусы.
✓ Свои заказы✓ Принудительный переход статуса✓ Изменить адрес ✓ Контрольный звонок (чек-бокс)✓ Лог действий✓ Примечания ✓ Запрос на отмену → нач. КЦ✓ Эскалация нач. КЦ ✓ Одобрить/Брак фото✗ Возврат денег напрямую ✗ Отмена заказа финально✗ Видит чужие заказы
🚴
Логист
Видит все заказы (как начальник КЦ по объёму видимости). Специализируется на назначении и мониторинге курьеров. Кнопка «Изменить/Добавить курьера» есть у логиста и начальника КЦ, но не у оператора.

Правило маршрутизации входящих звонков
Звонок клиента → сначала прикреплённому оператору. Если оператор занят более 20 секунд → переход к любому свободному оператору. Свободный оператор видит заказ через поиск, может дать справку и добавить примечание, но не может изменять статусы.

01
Создание Начальника КЦ
ℹ️
Создаётся системным администратором
Начальник КЦ создаётся в Admin Panel. Минимум один активный начальник КЦ на каждую смену.
1
Admin Panel → Пользователи → Создать пользователя
Раздел управления пользователями.
2
Заполнить профиль
ФИО, Логин (формат: sup.фамилия), Email, Телефон, Пароль (мин. 10 символов).
3
Роль: supervisor
Автоматически открывает: видимость всех заказов, кнопки отмены/возврата, карту курьеров, панель «Команда», Stop-List, Offline-режим ресторана.
4
Привязать к смене
Смена 1 (05:00–12:00) или Смена 2 (12:00–23:00). Можно привязать к обеим — тогда видит заказы круглосуточно.
5
Проверка
При входе: в правом углу 👑 Начальник КЦ, видны все заказы, активна карта, вкладка «Команда & Эскалации».
ПараметрЗначение
Роль в БДusers.role = 'supervisor'
ВидимостьВсе заказы без фильтра по operator_id
WebSocketПодписан на operators.* — все события всех заказов
Первый входПринудительная смена временного пароля

02
Создание оператора
⚠️
Один логин = одна сессия
Если оператор входит с другого устройства — предыдущая сессия завершается. Нельзя использовать один логин для двух операторов-сменщиков.
1
Admin Panel → Пользователи → Создать оператора
Начальник КЦ или системный администратор создаёт аккаунт.
2
Профиль
ФИО (отображается в карточке как «Оператор: Алишер М.»), Логин (формат: op.имя), Телефон, Пароль.
3
Роль: operator
Ограничивает видимость: оператор видит только orders WHERE operator_id = его user_id. Кнопки «Отмена», «Возврат», «Карта» скрыты.
4
Привязать к смене и рабочему месту
Смена: 1 или 2. Рабочее место: номер ПК (1–N). Используется алгоритмом автораспределения заказов.
5
Статус активности
user.status = 'active'. До активации оператор не получает заказы. Деактивация ('inactive') применяется при увольнении или длительном отпуске — не удаляет историю.
6
Проверка при первом входе
В правом углу: 👤 Оператор + имя. Вкладка «Мои заказы» пустая (нормально). Тест: назначить тестовый заказ через нач. КЦ → убедиться что заказ появился.

🚫
Один логин = одна сессия = одно рабочее место
Если оператор входит с другого ПК — предыдущая сессия завершается, workstation_id обновляется. Нельзя залогиниться одновременно на двух ПК. Резервный оператор (напр. Оп. 5 на Месте 2) должен иметь отдельный аккаунт.

🔄
Механизм смены оператора при переходе смены
В 12:00 система автоматически обновляет orders.operator_id для всех активных заказов: новый operator_id = тот, кто вошёл в систему за этим рабочим местом в Смену 2. Если никто не вошёл — заказы остаются на предыдущем операторе + автоэскалация начальнику КЦ через 5 мин.
⚠️ Известные ограничения алгоритма A
ПроблемаТехническое решение
Потеря контекста при сменеОбязательные примечания и лог действий в карточке заказа. Новый оператор видит всю историю.
Переход в горячий момент (12:00)Начальник КЦ вручную через «Изменить оператора» перераспределяет критические заказы до 12:00.
Рабочее место пустуетАвтоэскалация начальнику КЦ через 5 мин после начала смены, если за местом никто не залогинился.

04
Жизненный цикл заказа — статусы и переходы
ℹ️
Общее правило принудительных переходов
Любой принудительный переход статуса (кнопки оператора) требует выбора причины из enum-списка. При причине «Иное» — обязательный комментарий. Все переходы фиксируются в order_status_logs с user_id, timestamp и причиной.
🔵
1. Новые SLA 15 мин
▼
⏰
SLA-таймер: логика активации
Таймер 15 мин запускается в момент создания заказа. Если ресторан закрыт — hold_until_at = время открытия ресторана; таймер не запускается до этого момента (ночной режим, см. раздел 8). Таймер — чисто фронтовый countdown на основе sla_deadline_at. Пересчёт каждую секунду.

Логика переходов из статуса «Новые»

↕ Ветвление по результату подтверждения ресторана
✓ Ресторан нажал
Автоматический переход → Принято рестораном
Таймаут 15 мин
Система: alert-попап у оператора. Оператор звонит и если ресторан подтвердил голосом → нажимает «Принято рестораном» (принудительный переход, причина: «Голосовое подтверждение»)
Ресторан отказал
Оператор: «Запрос на отмену» с причиной → эскалация нач. КЦ → нач. КЦ нажимает «Отмена» с возвратом через Click API
Клиент хочет отменить
До 3 часов до «Готовится»: «Запрос на отмену» → нач. КЦ → полный возврат. После — только переадресация адреса, без возврата.

✓ Принято рестораном

Кнопки только у Начальника КЦ

👤 Изменить оператора

08
Ночной режим — заказ когда ресторан закрыт
🌙
Сценарий
Клиент хочет оформить заказ ночью, когда ресторан закрыт. Система показывает закрытые рестораны с информацией о времени работы и кнопкой «Сообщить когда откроется».
📱 Логика в Client APP (мини-апп Click)
1
Закрытый ресторан — состояние карточки
Ресторан отображается с пометкой о времени работы (например, «Открывается в 09:00»). Все блюда видны (картинки, описания, цены), но кнопка «Заказать» недоступна (disabled). На каждом блюде и у названия ресторана — галочка «Сообщить когда откроется».
2
Подписка на уведомление
Клиент ставит галочку → POST /notifications/subscribe с user_id + restaurant_id (или product_id). Запись в таблицу notification_subscriptions. Один клиент может подписаться на несколько ресторанов/блюд.
3
Утреннее уведомление
В момент открытия ресторана (по расписанию branch.opening_time): система автоматически отправляет Push + SMS всем подписавшимся клиентам. Текст: «Ресторан {название} открылся! Ваши любимые блюда доступны для заказа.»
4
Клиент оформляет заказ
Клиент заходит и заказывает. Создаётся заказ со статусом «Новый».

Описывается только техническая сторона: какие кнопки, переходы, поля и события задействованы при каждом инциденте. Операторские скрипты и звонки — вне данного документа.

Клиентские ситуации
5 инцидентов (1–2, 4–5, 9)▼
#1
Клиент хочет отменить заказ
Средний
Техническая логика
До 3 часов до «Готовится»: «Запрос на отмену» → эскалация нач. КЦ → Click API возврат → статус «Отменяется». После: кнопка «Запрос на отмену» отображается, но система фиксирует timestamp и блокирует возврат денег если нарушена оферта. Нач. КЦ принимает решение вручную.
Блокировка кнопки «Готовится» у ресторана
При заявке клиента на отмену вблизи дедлайна нач. КЦ нажимает «Приостановка» → cooking_lock = true → кнопка «Готовится» в Merchant App становится неактивной. Снимается после решения спора.
#2
Клиент хочет изменить состав заказа
Низкий
Техническая логика
Технически невозможно. После оплаты состав заказа заблокирован для изменений. В Client APP кнопка редактирования состава отсутствует. Оператор не может изменить — только адрес доставки.
Что доступно
Только изменение адреса доставки (кнопка «📍 Изменить адрес» доступна до статуса «Готовится»). Состав — never editable after payment.
#4
Клиент не отвечает на звонки (заказ прибыл)
Высокий
Двойной контакт — обязательное требование
В системе обязательно должны быть заполнены два номера клиента. При создании заказа через Click Super App — оба поля обязательны. Валидация на уровне формы заказа.
Закрытие без возврата
После 10 мин ожидания: оператор → «Запрос на отмену» с причиной «Клиент не найден» → нач. КЦ закрывает заказ без возврата (услуга доставки оказана, товар скоропортящийся). orders.closure_reason = 'client_not_found'. Фиксация в профиле клиента.
#5
Курьер не отвечает на звонки
Высокий
GPS-детектор
Если стоит > 5 мин при активном заказе → автоматическая угроза. Кнопка «Связаться с логистом» у оператора. Логист нажимает «Добавить/Изменить курьера» для назначения резерва.
Резервный курьер
Логист/нач. КЦ: «Добавить/Изменить курьера» → выбор свободного → обновление orders.courier_id → уведомление новому курьеру в Courier App.
#9
Неверный или уточняемый адрес
Средний
До выезда
Кнопка «📍 Изменить адрес» → попап с картой → клиент указывает точку + причина → обновляется orders.delivery_address + delivery_lat/lng. Уведомление курьеру автоматически.
В пути
Нач. КЦ оценивает рентабельность. При одобрении — тот же механизм изменения адреса. При отказе — заказ идёт по прежнему адресу.

Проблемы ресторана
7 инцидентов (3, 6–8, 10, 18–19)▶
#3
Риск опоздания из-за курьера
Высокий
Умный GPS-детектор
Параметры: стоянка > 7 мин AND расстояние > 1 км AND до дедлайна < 20 мин → автоматический перевод в «Угрозу». Параметры настраиваются в Admin Panel → sla_configs. Уведомление оператору WebSocket + push.
Экстренный курьер
Логист нажимает «Добавить курьера» → назначение резерва. orders.courier_id обновляется. Старый курьер получает уведомление об освобождении.
#6
Ресторан не отвечает на звонки
Высокий
Мин. 3 контакта в базе
При подключении ресторана к платформе обязательны минимум 3 номера (менеджер, кухня, администратор). Валидация при создании филиала в Admin Panel.
Экстренный визит
Логист отправляет резервного курьера для проверки. В панели — кнопка «Связаться с логистом» → уведомление в систему. Оператор создаёт инцидент.
#7
Ресторан перепутал заказ
Высокий
Фотоконтроль
Фотоотчёт ресторана (открытая тогора) служит основой для сравнения. Оператор видит состав из заказа и фото — сравнивает визуально. Кнопка «Брак — ресторану».
Инцидент
Оператор создаёт запись в inc_log. Нач. КЦ при подтверждении вины ресторана — возврат через Click API + фиксация в профиле ресторана для штрафных санкций.
#8
Курьер перепутал заказ
Высокий
Сверка в Courier App
Курьер видит фотоотчёт ресторана прямо в Courier App. Сверка при погрузке: ID заказа на фото должно совпадать с ID в приложении.
При обнаружении
Логист назначает нужного курьера через «Добавить/Изменить курьера» или отправляет запасного. Создаётся инцидент.
#10
Ресторан не успеет приготовить / Перекидка
Критический
«Перекидка» — техническая схема
1. Оператор: «Запрос на отмену» с причиной «Перекидка — нашли замену» → нач. КЦ. 2. Нач. КЦ: Click API возврат денег по исходному заказу → статус «Отменяется». 3. Клиент получает возврат. 4. Создаётся новый заказ в новом ресторане — клиент платит заново (Перекидка с созданием нового заказа MVP-версия).
Блокировка при последнем моменте
Нач. КЦ: branch.status = 'offline' → ресторан исчезает из Client APP → новые заказы не поступают. Все текущие заказы в этом филиале — проходят массовое рассмотрение.
#18
Ресторан изменил ингредиенты блюда
Высокий
Визуальная сверка
Оператор сравнивает фотоотчёт ресторана с составом заказа. При несоответствии: «Брак — ресторану» → push в Merchant App → ресторан переделывает.
Возврат при подтверждении
Нач. КЦ: полный возврат через Click API. Фиксация инцидента в профиле ресторана.
#19
Несоблюдение санитарных норм
Высокий
Фото-подтверждение
Фотоотчёт ресторана фиксирует состояние на момент отправки. При жалобе клиента — доказательная база. Кнопка «Брак» с причиной «Санитарные нормы».
Инцидент
Нач. КЦ: возврат + фиксация. При системных нарушениях — Stop-List ресторана.

Логистические инциденты
8 инцидентов (11–17, 21–23)▶
#11
Технические неполадки в системе
Критический
Резервный режим
Должна быть реализована синхронизация данных системы с Google Sheets в реальном времени. При сбое АРМ операторы и логисты работают по синхронизированной таблице. Последнее актуальное состояние заказов всегда доступно в резервной таблице.
Восстановление
После восстановления системы: сверка данных резервной таблицы с БД. При расхождении — ручная коррекция нач. КЦ через Admin Panel.
#12
Технические неполадки у курьера (связь/телефон)
Средний
Запасной телефон
Логист организует доставку запасного телефона (через Яндекс.Такси или резервным курьером). Курьер устанавливает Courier App на новый телефон и входит со своим логином/паролем — все активные заказы автоматически появляются.
Технически
Сессия привязана к user_id, не к устройству. Смена устройства не требует пересоздания назначений.
#13
Поломка автомобиля курьера
Критический
Перевалка тогоры
Логист отправляет подменную машину. В панели: «Добавить/Изменить курьера» → назначение резерва → обновление GPS-трекинга на новый транспорт. Уведомление новому курьеру.
Инцидент при невозможности
Если доставка невозможна — нач. КЦ: полный возврат через Click API. Фиксация инцидента.
#14–15–16
Потеря товарного вида / Несоответствие веса / Некомплект
Высокий
Фото как доказательная база
Все фотоотчёты хранятся в системе. При рекламации — сравнение фото ресторана (до отправки) с фото клиента (после получения). Кнопка «Рекламация → Инцидент» у завершённого заказа.
Частичный возврат
Нач. КЦ может провести частичный возврат через Click API (разница в стоимости некомплекта). Или полный — при полной порче. Фиксация в профиле ресторана.
#17
Нарушение температурного режима
Средний
Разделение заказа
Логист назначает две машины с разными термосумками. Технически: заказ разбивается на два delivery_parts с разными courier_id. В карточке оператора отображаются оба курьера.
При нарушении
Нач. КЦ: возврат + инцидент. Фиксация причины на стороне логистики.
#21
Локационные барьеры (сложный заезд)
Низкий
Напарник
Логист добавляет напарника: «Добавить курьера» → второй курьер назначается к тому же заказу как courier_helper_id. Уведомление обоим.
Примечание
Оператор фиксирует особенности заезда в примечаниях заказа — видны курьеру в Courier App.
#22
Несоответствие транспорта габаритам
Средний
Алгоритм назначения
Автоматически: 1–3 тогоры → одна машина. 4+ тогоры → несколько машин (из расчёта 3 тогоры на машину). При несоответствии система предупреждает логиста.
Ручная корректировка
Логист вручную изменяет количество машин до этапа погрузки через «Добавить/Изменить курьера».
#23
Заветривание блюда
Средний
Контроль по статусам
Регламент сборки: не ранее чем за 30 мин до выезда. Система фиксирует время перехода в «Готово к отправке» — оператор видит сколько времени тогора ждёт курьера. При превышении 30 мин — предупреждение.
При жалобе
Нач. КЦ: полный возврат. Инцидент фиксируется с timestamp ожидания как доказательство.

Инциденты без прямой строки и системные
4 инцидента (20, 24 + 2 системных)▶
#20
Поведение курьера (жалоба клиента)
Низкий
Фиксация
Оператор: «Рекламация → Инцидент» из статуса «Завершено». Описание в логе. Нач. КЦ: решение о компенсации + фиксация в профиле курьера.
Системная часть
При системных нарушениях — нач. КЦ может временно отстранить курьера: courier.status = 'suspended' до выяснения причин.
#24
Инцидент без прямой строки в таблице
Любой
Технический механизм
Единый лог действий по заказу: оператор фиксирует время, кто звонил, суть, договорённости. Эскалация нач. КЦ обязательна. Нач. КЦ через Admin Panel создаёт новую строку в таблице инцидентов для последующего пополнения регламента.
SLA-контроль
Нельзя обрывать коммуникацию без решения по SLA. Система фиксирует открытый инцидент до явного закрытия нач. КЦ.
СИС-1
Технический сбой при переходе статуса
Критический
Логика
Если курьер начал движение, но автопереход «Готово к отправке» → «В пути» не сработал: оператор нажимает принудительный переход. Нач. КЦ может через Admin Panel принудительно зафиксировать время начала движения для корректного ETA.
Завершение
При сбое перехода в «Завершено»: кнопка «✓ Отменено (ручное)» — принудительное закрытие. Проверка корректности статуса в Click Super App клиенту.
СИС-2
Ошибочное двойное списание / дубль заказа
Критический
Обнаружение дубля оператором
Оператор видит два идентичных заказа → «Запрос на отмену» с причиной «Технический дубль» → нач. КЦ. Нач. КЦ: сверка транзакций в Click API → возврат по одному из дублей до начала приготовления.
Ошибка двойного списания
Нач. КЦ: проверка истории транзакций → возврат излишне списанной суммы через Click API → уведомление клиенту.

Источники для сравнения
Таблица угроз (24 инцидента), Регламент оператора MVP, Регламент логиста MVP, Регламент начальника КЦ MVP — сравниваются с реализацией АРМ v6.

Правило 3-х часов до «Готовится»

Принудительный переход статуса с причиной
